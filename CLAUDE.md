# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

InSite Assurance: a multi-tenant field-evidence and drawdown-reconciliation platform for construction finance. An npm-workspaces monorepo, Node 24 (`.nvmrc`), npm 11:

| Workspace | Stack | Role |
| :--- | :--- | :--- |
| `shared` (`@insite/shared`) | TypeScript, Zod, Turf | Enums, every request/DTO schema, permission catalog, default roles, geofence maths, shared data (standards library). Single source of truth for contracts. |
| `server` (`@insite/server`) | Express, Prisma 7 (`pg` adapter), PostgreSQL | REST API under `/api/v1`, voice-note transcription (Whisper; the only model called), S3-compatible storage (local-disk mode in dev/tests), PDF. CommonJS. |
| `web` (`@insite/web`) | React, Vite, React Query, Tailwind 3 | Portal for monitors, lenders, contractors, tenant admins. |
| `mobile` (`@insite/mobile`) | Expo / React Native, SQLite | Offline-first field app with one outbox. |

**This branch (`UBEC`) is being redesigned for one programme client: read `saas_updates/client_flow_redesign.md` first; it overrides earlier decisions where they conflict. Redesign work is tracked in `saas_updates/redesign_r1_implementation_plan.md` and `redesign_r2_implementation_plan.md` (and later R files).** The SaaS migration is run phase by phase from `saas_updates/`. **Before working on a phase, read `saas_updates/saas_implementation_plan.md` sections 2, 3 and 6 (decisions and conventions), then the phase file.** Record findings in the phase file's "Found during implementation" section rather than widening scope. Product background: `Project Context/project_context_current.md`.

## Working on a plan (phase or redesign slice): fast without losing quality

Follow these steps in order for any plan file (`saas_updates/*_implementation_plan.md`).

1. **Read the context, once and targeted.** Read the plan, `saas_updates/redesign_contracts_r3_r7.md` (it wins over the plans), the previous plan's "Found during implementation" section and the files the plan's "Read first" list names. Read only what the slice touches; use `grep` to locate code before opening files.
2. **Clarify before building.** After reading, list every open point in one batch and ask the owner in a single round (AskUserQuestion, at most 4 questions, recommended option first):
   - each `(confirm)` decision you would build differently from its default;
   - conflicts between the plan, the contract register and the code as it is now;
   - facts the plan assumes that the seed or code contradicts.
   
   Do not ask about defaults you would keep: build them and record them. After this round, do not stop again for questions. Decide, record the decision in the plan's "Found during implementation" section, and continue.
3. **Baseline from the record, not a rerun.** Take the baseline numbers from the previous plan's verification table. Rerun the full suite only if the working tree changed since then (`git status`, migrations not yet applied).
4. **Contracts first, then parallel work.** Write and build the slice's shared schemas and pure functions first (`npm run build:shared`). Once they are fixed, the owner's standing instruction is to parallelise independent work with subagents:
   - server services, routes and route tests;
   - web API, queries, mutations and components;
   - mobile, when the slice has mobile work;
   - docs (`CLAUDE.md`, `configuration_reference.md`, the demo script) while the final checks run.
   
   Give each agent the shared contract names, the files it owns, and the files it must not touch, so two agents never edit the same file. Keep migrations, the Prisma schema and the seed in one agent (or the main thread), because they must stay sequential.
5. **Check cheaply inside a slice, fully at boundaries.**
   - While working: `npm run typecheck` plus only the affected test files (`npx tsx --test --test-concurrency=1 src/tests/<file>`, about 20 s each).
   - Run the full gate (typecheck, lint, web build, server unit + route tests, mobile tests, seed) in the background (`run_in_background`) at the end of every second or third slice, before any slice that deletes code, and at the end. Write docs while it runs.
   - The "each slice green" rule still holds: a slice is not ticked until the gate that covers it has passed.
6. **Edit efficiently on Windows.** For multi-line scripted edits, write the Node script to a scratch file with the Write tool. Never put template literals in heredocs or `node -e`. Normalise `\r\n` in the script and restore the file's original line endings when writing it back. Prefer the Edit tool for single edits.
7. **Record as you go.** Fill the plan's verification table (baseline, each gate), migrations, `(confirm)` outcomes and findings while working, not at the end.

## Architecture

**Contracts first.** Every request body and DTO is a Zod schema in `shared/src/schemas`, exported from `shared/src/index.ts`. Web and mobile import types from `@insite/shared`; never hand-write duplicates. New permissions go in `SYSTEM_PERMISSIONS_CATALOG` (`shared/src/enums.ts`) and the default roles (`shared/src/defaultRoles.ts`). New audit actions go in both the shared enum and the Prisma `AuditActionType` enum.

**Server request path.** `server/src/app.ts` mounts routers; most are mounted at `/api/v1/projects`. A project router is wrapped with `guardProjectRoutes` (`server/src/utils/accessControl.ts`), which authenticates any principal (web user, or provisioned mobile account resolved to its field session for the URL project), checks tenant/assignment or project visibility, and applies lifecycle rules: a DRAFT project serves only the routes in `DRAFT_ROUTE_RE`; an ARCHIVED project is read-only. Route files stay thin (permission guard, `validateBody(schema)`, call a service). Never read a resource by an ID from the body without confirming it belongs to the URL project (`server/src/utils/ownership.ts` loaders). State changes go in one `prisma.$transaction` together with `recordAuditEvent` (hash-chained ledger). Responses are built by explicit serializers, never by spreading Prisma rows. Principals: `req.webUser`, `req.fieldAgent` (`fieldPersonaType`, `userId`), `req.mobileUser`.

**No contractor login (redesign R1d, decision P2).** There are two token types: web (`WEB_USER`) and mobile account (`MOBILE_USER`). Join codes, join-code sessions, the field-session token, identity assurance (ID + selfies), `/auth/device-key` and the public handover link are deleted. Every MOBILE/BOTH role is a provisioned-account role; a `FieldAgentSession` is one account on one project from one device (`userId` required), created by `findOrCreateProvisionedSession` (`modules/auth/mobileAccess.ts`). No default role has the `CONTRACTOR_EXECUTOR` persona and the role editor refuses it (`AssignableFieldPersonaTypeEnum`); the enum value remains only because the old mobile app's tests reference it (R5 removes it). The contractor is an organisation record on the project (one per project, decision T: no execution modes, no main contractor, no replacement; `syncProjectContractors` refuses a second). Defects and inspection findings are staff-only. Contractor-side branches still in documents, ratings, lessons and web notifications (`targetOrganizationId`, `hideFromProjectContractors`, `visibleToContractors`) are unreachable and go with R6 (R4 left them, see the R4 plan section 10). The contractor only gets emails (kick-off notice, the R4 findings summary). Tests authenticate field sessions with `server/src/tests/helpers/fieldAuth.ts` (`createFieldSession`, `fieldAuth`).

**Process engine (Phase 7).** Per-project `ProjectProcessConfig` (read via `getProcessConfig`, memoised per request through `server/src/utils/requestContext.ts`; a project with no row behaves as `DEFAULT_PROJECT_PROCESS_CONFIG`). Services branch on it: report approval, hold points, contractor field reporting, identity assurance, the report checks (rules), handover and retention modules. Approval chains are versioned `ApprovalStep` rows: edits write a new version, items in flight keep theirs. Engine: `server/src/modules/process/approvalChain.ts`. Chain types: `REPORT` and `CONTRACT_DEFAULT` (the lender disbursement chain was removed in redesign R1b).

**Cadence and scheduled jobs (Phase 8, reduced in R4f).** Period maths is pure and shared: `shared/src/utils/reportingPeriod.ts` (`getReportingPeriodForDate`, `listWorkdaysInPeriod`, `nextPeriodStart`, also `addDays`/`isoWeekday` that R4 uses; R5 moves those before deleting the file). `server/src/modules/cadence/cadence.service.ts` maps a project onto it (`cadenceSettingsForDate` honours a pending cadence change, `periodKeyForDate`, `lateness`); workday reports and the old app's pack still use it until R5. Redesign R4f deleted reporting streams, reporting obligations, the cadence reporter scopes, the `reporting` setup step, the type keys `reportingStreams`/`reportingDefaults`, the `/cadence` and `/reporting-obligations` routes and the jobs `reporting-obligations` and `overdue-reports`: visits replace them. Reports carry `reportingPeriodStart/End` and `dueAt`; one original report per reporter, item and `reportingPeriodStart` (hand-written partial unique index `workday_reports_one_report_per_period`, keep it). Jobs live in `server/src/jobs/` (`message-dispatch`, Phase 9 `schedule-variance`, Phase 13 `milestone-deadlines`, Phase 16 `kpi-snapshot`, R4 `visit-reminders`, `visit-deadlines`, `finding-escalations`), registered by `registerAllJobs()`; each tick holds `pg_try_advisory_xact_lock` and each unit claims a `JobRun` row via `runUnit(jobName, scopeKey, fn)`. Construction jobs touch ACTIVE projects of non-suspended tenants (`LIVE_PROJECT_WHERE` in `cadenceJobs.ts`); the visit jobs every ACTIVE project in every phase (`VISIT_PROJECT_WHERE`). Tests run a tick with `runJobOnce(name, now)`. `JOBS_ENABLED=false` turns them off in a process. Outbound messages: `server/src/integrations/messaging` (`sendMessage`, adapters console/resend/push, SMS empty; tests read `consoleOutbox` or use `setMessageAdapterOverrides`). Redesign R1e deleted morning briefs, presence telemetry and manual check-in, the mobilisation participant roster, attendance alerts and their jobs, and the executive risk matrix (`/app/executive` redirects to the portfolio). The omission check's photo rule: a report with progress needs a photo or a reason. Mobile computes the period from the baseline pack's `cadence` via `mobile/src/utils/projectCadence.ts`.

**Schedule (Phase 9, reduced in redesign R2d).** The baseline, earned-schedule variance, `BoqItemDependency`, `ScheduleRevision`/"Catch Project Up", the Schedule setup step and page are deleted. What remains: `shared/src/utils/schedule.ts` (`addWorkdays`, `windowEnd`, `windowOverlaps`, `itemPeriodStatus`), actual dates in `server/src/modules/schedule/schedule.service.ts` (`recordItemActualStart` wherever a report becomes counted; `syncActualCompletionDates` inside `refreshProjectProgress`), and the badge. Line planned windows come from sprints (D-R2.5, below). The `schedule-variance` job stores `Project.scheduleStatus` from sprints (`refreshScheduleBadge` → `sprintScheduleStatus` in `shared/src/utils/scope.ts`: UNSCHEDULED without sprints, COMPLETE when every line is at 100%, NOT_STARTED before sprint 1, BEHIND when a unit whose end sprint has ended still has a line below 100%, ON_TRACK otherwise; redesign R4e: sprint verification decides, see Visits) and notifies `schedule:view_variance` holders once when a project falls behind. The badge (`ScheduleVarianceBadge`: status, label, computedAt; no variance in working days) shows on the directory, dashboard and portfolio map.

**Facilities, scope and sprints (redesign R2).** Spec: `client_flow_redesign.md` sections 5–7; plan: `saas_updates/redesign_r2_implementation_plan.md`. Facility catalogue: tenant `Facility` rows (code, name, category, archetype `BUILDING_WORKS | SUPPLY_INSTALLATION | UTILITIES | EXTERNAL_WORKS`, `isRetired`), provisioned from `DEFAULT_FACILITIES` (50, `shared/src/schemas/facility.schema.ts`) in `createTenantWithDefaults`, the seed and lazily on first read (`ensureFacilities`); `/api/v1/facilities` (read: any web user; write: `facilities:manage`); a code is locked once a unit uses it; retired facilities stay on projects and leave pickers and the workbook. Project scope (`server/src/modules/scope/`): `ProjectSprint` (numbers follow date order, overlaps refused, status derived: UPCOMING/ACTIVE/ENDED), `FacilityUnit` (workbook "Unit ID" unique per project, start/end sprint, planned quantity required for supply units), scope lines are `BoqItem` rows with `facilityUnitId` (amount = `lineAmount(qty, rate)`, server-computed; `section` = facility name). Pure rules in `shared/src/utils/scope.ts` (`validateSprints`, `validateUnits`, `deriveSprintStatus`, `unitsActiveInSprint`, `lineAmount`, `sprintScheduleStatus`); `UNITS_OF_MEASURE` is a fixed shared list. Every write goes through `runScopeWrite` (project row locked, one transaction, audit `SPRINTS_SAVED`/`SCOPE_UPDATED`, `deriveLineDatesFromSprints` sets each line's planned window from its unit's sprints and the project's planned start/end from the first/last sprint, progress refresh on live projects, the `scope` setup step marked saved on drafts). A unit or line with captures, reports, defects or progress cannot be removed; on a live project a sprint a unit starts or ends in cannot be removed (on a draft its units lose it). Routes (`scope.routes.ts`, `boq:view` to read, `boq:upload_edit` to write): `GET /scope`, `PUT /scope/sprints` (full list), units and lines CRUD. Setup step `scope` (replaces `boq`) is required: at least one sprint, one line, every line on a unit, every unit with both sprints (D-R2.6; projects live before R2 without units are not flagged). Needs-assessment workbook (`modules/scope/workbook/scopeWorkbook.ts`, pure, reusable by the Needs Assessment module): `buildScopeWorkbook` (Instructions with the `SCOPE_WORKBOOK_VERSION` stamp, Project, Facility units, BoQ, Sprints, hidden protected Lists; dropdowns, Amount formula, date validation; pre-filled from the project) and `parseScopeWorkbook` (columns by header name, version check, row-level issues, amounts recomputed, a cleared row's stale Amount ignored). `scopeImport.service.ts`: `GET /scope/workbook`, `POST /scope/import/preview` (nothing written) and `/confirm` (same sha256 as the preview or 409 `SCOPE_IMPORT_FILE_CHANGED`; errors 422 `SCOPE_IMPORT_INVALID`; replaces the draft's sprints, units and lines in one transaction; fills only empty project fields from the Project sheet, incl. `siteAddress`, `strategicJustification`, `assumptions`, a primary SCHOOL beneficiary, the delivery model (type applied) and a radial geofence of the workspace default radius from the GPS point; audit `SCOPE_IMPORTED`). The blank workbook (workspace lists, nothing pre-filled) is `GET /api/v1/scope-workbook` (any web user; Settings → Facilities); the project workbook is also offered in the needs-assessment section of the Standards step. Live projects refuse import (409 `SCOPE_IMPORT_LIVE_PROJECT`). The programme of works is a `PROGRAMME_OF_WORKS` document (`requiresSignOff`); its sign-off completes `AUTO_SCHEDULE_BASELINE_SET` ("Programme accepted") milestones. Web: Settings → Facilities (`components/facilities/FacilitiesCard.tsx`), `components/scope/ScopeAndSprintsPanel.tsx` + `ScopeWorkbookToolbar.tsx` used by the setup step `ScopeStep` and the project page `/app/projects/:id/scope` ("Scope & sprints" replaces "BOQ & hold points"; `/boq` and `/schedule` redirect there). Mobile still reads `GET /boq`.

**Geofences (redesign).** A site boundary is radial or a perimeter; linear corridors and chainage (`FieldEvidenceLog.chainageKm/chainageLabel/corridorOffsetMeters`, `WbsChatMessage.chainageLabel`) were removed (migration `20261208090000_geofence_default_radius_no_corridors` turned corridor projects into a bounding-box perimeter). `Tenant.defaultGeofenceRadiusMeters` (Settings → Workspace settings, 20–50,000, default 150, `DEFAULT_GEOFENCE_RADIUS_METERS`) pre-fills a new radial boundary in `GeofenceEditor` (`defaultRadiusMeters`, from `setup.site.tenantDefaultRadiusMeters`) and the workbook GPS boundary; each project keeps its own radius in its geofence (Site step). The tolerance band (`defaultGeofenceToleranceMeters`, project override) is unchanged. Seeded LKK-402 is a perimeter along the road.

**Handover, retention and defects (Phase 10).** `Project.constructionPhase` (`ACTIVE_CONSTRUCTION → HANDOVER_IN_PROGRESS → RETENTION_PERIOD → COMPLETED_CLOSED`, only backwards move handover → construction) sits beside `status`; transitions in `server/src/modules/closeout/projectPhase.service.ts`, table and retention maths in `shared/src/utils/retention.ts`. All closeout routes (`closeout.routes.ts`) answer 404 unless `enableHandoverModule` / `enableRetentionModule` is on (`closeoutGate.ts`). After construction: `assertConstructionOngoing` refuses new reports; `LIVE_PROJECT_WHERE` excludes the project from construction jobs; field sessions may only write defect work (`FIELD_DEFECT_WORK_RE` in `accessControl.ts`). Handover (R1d): an officer with `handover:record_response` records the beneficiary's response from the signed paper copy (`POST /projects/:id/handover/submissions`, `RecordHandoverResponseRequestSchema`, attestation required, only in HANDOVER_IN_PROGRESS); a user with `handover:review_feedback` reviews it, which issues the handover certificate when accepted; snags convert to defect tickets. Files under `.../handover/` from the old public link stay quarantined (`isHandoverObjectKey`). Stakeholder text is sanitised plain text (`shared/src/utils/handoverText.ts`), rendered by `RichTextView`, never as HTML. Retention is held against recorded payments (see Payments below); `Project.retentionHeldNgn` is the balance still held, `retentionReleasedNgn` the total released. Release: record a `RETENTION_RELEASE` payment; `GET /retention` reports the balance and the liability period. Defects are staff-only (R1c/R1d): `defectViewerFor` is a staff viewer (`retention:manage_defects`); tickets name the project's contractor (`liableContractorId`); "assign" records that the ticket was passed to the contractor; closing needs the officer's site photos (field app, `verify` CLOSE with captures); a ticket awaiting verification can be reopened; there is no rectify step. Job `defect-reminders` (staff summary only). Mobile: `DefectsScreen`, outbox kind `DEFECT_ACTION` (verify only, waits on its captures).

**Delivery models (Phase 11).** Client rules are data on a project type or the tenant (decision J). `Organization.parentOrganizationId` forms a hierarchy (max 5 levels, cycles refused by `validateOrganizationParent` in `shared/src/utils/organizationHierarchy.ts`; server helpers in `server/src/modules/organizations/hierarchy.ts`). `Project.owningOrganizationId` is the accountable owner; the funder is still `lenderOrganizationId` (shown through terminology). Visibility: `projectAccessBranch` in `accessControl.ts` is the one rule for lists and the guard (assigned, or `projects:view_all_tenant`, or `projects:view_organization_tree` + owner in the user's subtree, expressed as nested parent relations so it composes into any `where`); mobile accounts follow the same rule. Approval steps carry `organizationScope` (`ANY`, `PROJECT_OWNER`, `PROJECT_OWNER_OR_ANCESTOR`, `FUNDER`); every `gateForStep` call must pass `orgContext` from `orgContextForStep` (no bypass, not even the platform super admin). `ProjectType` (`server/src/modules/projectTypes/`) references a workflow template and holds `ProjectTypeConfigSchema` (every key defaulted; reserved keys for Phases 12–16). Applying a type to a draft (`applyProjectTypeToProject`, from the Basics step or draft creation) copies the template, writes `projectTypeSnapshotJson` + `projectTypeVersion`, pre-fills owner/funder/reporting without overwriting saved values, and audits `PROJECT_TYPE_APPLIED`; on a live project the type is locked (409 `PROJECT_TYPE_LOCKED`). Read a project's rules with `resolveProjectTypeConfig(snapshot)` (null = no type = pre-Phase-11 behaviour); never read the live type for a project's rules. A tenant with active types must give new drafts a type. Regions (`server/src/modules/regions/`) are two levels. Beneficiaries are saved with the Parties step (exactly one primary). Terminology: `Tenant.terminologyLabels`, keys fixed in `shared/src/terminology.ts`; web uses `useTerm()` from `auth-context`, server uses `terminologyForProject` / `resolveTerminology`, mobile reads `useActiveBranding().terminology`. ## Environment gotchas (Windows)

- Shell is Git Bash plus PowerShell; there is no Python. Many source files use CRLF line endings, so scripted find-and-replace must normalise `\r\n` or it silently matches nothing; prefer the Edit tool.
- Do not put template literals (backticks) or `${...}` inside inline `node -e "..."` or heredoc commands in bash: they get expanded or break parsing. Write the script or content to a scratch file first.
- The server compiles to CommonJS: ESM-only packages (e.g. `unpdf`) must be loaded with a real dynamic import (see `server/src/integrations/textExtractor.ts`).
