# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

InSite Assurance: a multi-tenant platform for monitoring the delivery of programme projects (on this branch, UBEC's school infrastructure: needs assessment to closure, with field visits from a phone app). An npm-workspaces monorepo, Node 24 (`.nvmrc`), npm 11:

| Workspace | Stack | Role |
| :--- | :--- | :--- |
| `shared` (`@insite/shared`) | TypeScript, Zod, Turf | Enums, every request/DTO schema, permission catalog, default roles, geofence maths, shared data (standards library). Single source of truth for contracts. |
| `server` (`@insite/server`) | Express, Prisma 7 (`pg` adapter), PostgreSQL | REST API under `/api/v1`, voice-note transcription (Whisper; the only model called), S3-compatible storage (local-disk mode in dev/tests), PDF. CommonJS. |
| `web` (`@insite/web`) | React, Vite, React Query, Tailwind 3 | Portal for programme staff, M&E officers and tenant admins. |
| `mobile` (`@insite/mobile`) | Expo / React Native, SQLite | Offline-first field app with one outbox. |

**This branch (`UBEC`) is being redesigned for one programme client: read `saas_updates/client_flow_redesign.md` first; it overrides earlier decisions where they conflict. Redesign work is tracked in `saas_updates/redesign_r1_implementation_plan.md` … `redesign_r7_implementation_plan.md` (R1–R6 done; R7a done: permission catalogue; R7b reduced to two server rules; the role set and the seed are deferred to `saas_updates/next_steps/role_catalogue_migration_plan.md` and `seed_replacement_plan.md`), with cross-plan names settled in `redesign_contracts_r3_r7.md`.** The SaaS migration is run phase by phase from `saas_updates/`. **Before working on a phase, read `saas_updates/saas_implementation_plan.md` sections 2, 3 and 6 (decisions and conventions), then the phase file.** Record findings in the phase file's "Found during implementation" section rather than widening scope. Product background: `client_flow_redesign.md` and the client's process design (`Project Context/MoE_Process Design for Direct & Matching Grant Project Delivery__Draft.pdf`); `Project Context/project_context_current.md` is the historical lender-product spec.

## Working on a plan (phase or redesign slice): fast without losing quality

Follow these steps in order for any plan file (`saas_updates/*_implementation_plan.md`).

1. **Read the context, once and targeted.** Read the plan, `saas_updates/redesign_contracts_r3_r7.md` (it wins over the plans), the previous plan's "Found during implementation" section and the files the plan's "Read first" list names. Read only what the slice touches; use `grep` to locate code before opening files.
2. **Clarify before building.** After reading, list every open point in one batch and ask the owner in a single round (AskUserQuestion, at most 4 questions, recommended option first):
   - each `(confirm)` decision you would build differently from its default;
   - conflicts between the plan, the contract register and the code as it is now;
   - facts the plan assumes that the seed or code contradicts.
   
   Do not ask about defaults you would keep: build them and record them. After this round, do not stop again for questions. Decide, record the decision in the plan's "Found during implementation" section, and continue.
3. **Baseline from the record, not a rerun.** Take the baseline numbers from the previous plan's verification table. Rerun the full suite only if the working tree changed since then (`git status`, migrations not yet applied).
4. **Contracts first, then parallel work.** Write and build the slice's shared schemas and pure functions first (`npm run build:shared`). Once they are fixed, the owner's standing instruction is to parallelise independent work with subagents:
   - server services, routes and route tests;
   - web API, queries, mutations and components;
   - mobile, when the slice has mobile work;
   - docs (`CLAUDE.md`, `configuration_reference.md`, the demo script) while the final checks run.
   
   Give each agent the shared contract names, the files it owns, and the files it must not touch, so two agents never edit the same file. Keep migrations, the Prisma schema and the seed in one agent (or the main thread), because they must stay sequential.
5. **Check cheaply inside a slice, fully at boundaries.**
   - While working: `npm run typecheck` plus only the affected test files (`npx tsx --test --test-concurrency=1 src/tests/<file>`, about 20 s each).
   - Run the full gate (typecheck, lint, web build, server unit + route tests, mobile tests, seed) in the background (`run_in_background`) at the end of every second or third slice, before any slice that deletes code, and at the end. Write docs while it runs.
   - The "each slice green" rule still holds: a slice is not ticked until the gate that covers it has passed.
6. **Edit efficiently on Windows.** For multi-line scripted edits, write the Node script to a scratch file with the Write tool. Never put template literals in heredocs or `node -e`. Normalise `\r\n` in the script and restore the file's original line endings when writing it back. Prefer the Edit tool for single edits.
7. **Record as you go.** Fill the plan's verification table (baseline, each gate), migrations, `(confirm)` outcomes and findings while working, not at the end.

## Architecture

**Contracts first.** Every request body and DTO is a Zod schema in `shared/src/schemas`, exported from `shared/src/index.ts`. Web and mobile import types from `@insite/shared`; never hand-write duplicates. New permissions go in `SYSTEM_PERMISSIONS_CATALOG` (`shared/src/enums.ts`, eight categories that follow the programme flow: Workspace & access, Forms & facilities, Portfolio & projects, Scope & sprints, Contract & kick-off, Visits & findings, Payments & retention, Completion & closure) and the default roles (`shared/src/defaultRoles.ts`; the UBEC roles are tailored in `seedUbecRoster.ts` until the role migration). New audit actions go in both the shared enum and the Prisma `AuditActionType` enum.

**Server request path.** `server/src/app.ts` mounts routers; most are mounted at `/api/v1/projects`. A project router is wrapped with `guardProjectRoutes` (`server/src/utils/accessControl.ts`), which authenticates any principal (web user, or provisioned mobile account resolved to its field session for the URL project), checks tenant/assignment or project visibility, and applies lifecycle rules: a DRAFT project serves only the routes in `DRAFT_ROUTE_RE`; an ARCHIVED project is read-only. Route files stay thin (permission guard, `validateBody(schema)`, call a service). Never read a resource by an ID from the body without confirming it belongs to the URL project (`server/src/utils/ownership.ts` loaders). State changes go in one `prisma.$transaction` together with `recordAuditEvent` (hash-chained ledger). Responses are built by explicit serializers, never by spreading Prisma rows. Principals: `req.webUser`, `req.fieldAgent` (`fieldPersonaType`, `userId`), `req.mobileUser`.

**No contractor login (redesign R1d, decision P2).** There are two token types: web (`WEB_USER`) and mobile account (`MOBILE_USER`). Join codes, join-code sessions, the field-session token, identity assurance (ID + selfies), `/auth/device-key` and the public handover link are deleted. Every MOBILE/BOTH role is a provisioned-account role; a `FieldAgentSession` is one account on one project from one device (`userId` required), created by `findOrCreateProvisionedSession` (`modules/auth/mobileAccess.ts`). The `CONTRACTOR_EXECUTOR` persona is gone (R5f). The contractor is an organisation record on the project (one per project, decision T: no execution modes, no main contractor, no replacement; `syncProjectContractors` refuses a second). Defects and findings are staff-only. Contractor-side branches still in documents, ratings, lessons and web notifications (`targetOrganizationId`, `hideFromProjectContractors`, `visibleToContractors`) are unreachable; R6 did not take them (left for R7). The contractor only gets emails (kick-off notice, the R4 findings summary). Mobile-only roles have no web sign-in (redesign R7b): a user whose main role surface is `MOBILE` (Resident Supervisor) gets 403 `WEB_ACCESS_NOT_ALLOWED` at web login and on any web token (`server/src/modules/auth/webAccess.ts`); `BOTH` roles use the same credentials on web and phone; platform super admins are never refused. Tests authenticate field sessions with `server/src/tests/helpers/fieldAuth.ts` (`createFieldSession`, `fieldAuth`).

**Process engine (Phase 7).** Per-project `ProjectProcessConfig` (read via `getProcessConfig`, memoised per request through `server/src/utils/requestContext.ts`; a project with no row behaves as `DEFAULT_PROJECT_PROCESS_CONFIG`). Services branch on it: report approval (visit submissions since R4), handover and retention modules (R5f removed hold points, contractor field reporting and the report-check switches). Approval chains are versioned `ApprovalStep` rows: edits write a new version, items in flight keep theirs. Engine: `server/src/modules/process/approvalChain.ts`. Chain types: `REPORT` and `CONTRACT_DEFAULT` (the lender disbursement chain was removed in redesign R1b).

**Scheduled jobs (Phase 8; cadence removed in R4f and R5f).** Reporting cadence, periods, streams, obligations and workday reports are gone (R4f, R5f): visits replace them. What remains of Phase 8: the project's working days `Project.workWeekDays` (visits use them) and `mobilizationReminderOffsetsDays`; calendar helpers `addDays`, `isoWeekday`, `daysBetween`, `zonedCalendarDate`, `DEFAULT_WORK_WEEK_DAYS`, `ISO_WEEKDAY_SHORT` in `shared/src/utils/calendar.ts`. Jobs live in `server/src/jobs/` (`message-dispatch`, Phase 9 `schedule-variance`, Phase 13 `milestone-deadlines`, Phase 16 `kpi-snapshot`, R4 `visit-reminders`, `visit-deadlines`, `finding-escalations`, UBEC IRL `project-alerts`), registered by `registerAllJobs()`; each tick holds `pg_try_advisory_xact_lock` and each unit claims a `JobRun` row via `runUnit(jobName, scopeKey, fn)`. Construction jobs touch ACTIVE projects of non-suspended tenants (`LIVE_PROJECT_WHERE` in `cadenceJobs.ts`); the visit jobs every ACTIVE project in every phase (`VISIT_PROJECT_WHERE`). Tests run a tick with `runJobOnce(name, now)`. `JOBS_ENABLED=false` turns them off in a process. Outbound messages: `server/src/integrations/messaging` (`sendMessage`, adapters console/resend/push, SMS empty; tests read `consoleOutbox` or use `setMessageAdapterOverrides`). Redesign R1e deleted morning briefs, presence telemetry and manual check-in, the mobilisation participant roster, attendance alerts and their jobs, and the executive risk matrix (`/app/executive` redirects to the portfolio). `jobs/cadenceJobs.ts` keeps its name; it only holds `LIVE_PROJECT_WHERE`.

**Schedule (Phase 9, reduced in redesign R2d).** The baseline, earned-schedule variance, `BoqItemDependency`, `ScheduleRevision`/"Catch Project Up", the Schedule setup step and page are deleted. What remains: `shared/src/utils/schedule.ts` (`addWorkdays`, `windowEnd`, `windowOverlaps`), actual completion dates in `server/src/modules/schedule/schedule.service.ts` (`syncActualCompletionDates` inside `refreshProjectProgress`; actual start dates are no longer recorded since R5f removed reports, their only source), and the badge. Line planned windows come from sprints (D-R2.5, below). The `schedule-variance` job stores `Project.scheduleStatus` from sprints (`refreshScheduleBadge` → `sprintScheduleStatus` in `shared/src/utils/scope.ts`: UNSCHEDULED without sprints, COMPLETE when every line is at 100%, NOT_STARTED before sprint 1, BEHIND when a unit whose end sprint has ended still has a line below 100%, ON_TRACK otherwise; redesign R4e: sprint verification decides, see Visits) and notifies `sprints:view_status` holders once when a project falls behind. The badge (`ScheduleVarianceBadge`: status, label, computedAt; no variance in working days) shows on the directory, dashboard and portfolio map.

**Facilities, scope and sprints (redesign R2).** Spec: `client_flow_redesign.md` sections 5–7; plan: `saas_updates/redesign_r2_implementation_plan.md`. Facility catalogue: tenant `Facility` rows (code, name, category, archetype `BUILDING_WORKS | SUPPLY_INSTALLATION | UTILITIES | EXTERNAL_WORKS`, `isRetired`), provisioned from `DEFAULT_FACILITIES` (50, `shared/src/schemas/facility.schema.ts`) in `createTenantWithDefaults`, the seed and lazily on first read (`ensureFacilities`); `/api/v1/facilities` (read: any web user; write: `facilities:manage`); a code is locked once a unit uses it; retired facilities stay on projects and leave pickers and the workbook. Project scope (`server/src/modules/scope/`): `ProjectSprint` (numbers follow date order, overlaps refused, status derived: UPCOMING/ACTIVE/ENDED), `FacilityUnit` (workbook "Unit ID" unique per project, start/end sprint, planned quantity required for supply units), scope lines are `BoqItem` rows with `facilityUnitId` (amount = `lineAmount(qty, rate)`, server-computed; `section` = facility name). Pure rules in `shared/src/utils/scope.ts` (`validateSprints`, `validateUnits`, `deriveSprintStatus`, `unitsActiveInSprint`, `lineAmount`, `sprintScheduleStatus`); `UNITS_OF_MEASURE` is a fixed shared list. Every write goes through `runScopeWrite` (project row locked, one transaction, audit `SPRINTS_SAVED`/`SCOPE_UPDATED`, `deriveLineDatesFromSprints` sets each line's planned window from its unit's sprints and the project's planned start/end from the first/last sprint, progress refresh on live projects, the `scope` setup step marked saved on drafts). A unit or line with progress or a defect cannot be removed (captures no longer name a line, R5f); a sprint a payment names cannot be removed (409 `SPRINT_IN_USE`, R6d); on a live project a sprint a unit starts or ends in cannot be removed (on a draft its units lose it). Routes (`scope.routes.ts`, `scope:view` to read, `scope:edit` to write): `GET /scope`, `PUT /scope/sprints` (full list), units and lines CRUD. Setup step `scope` (replaces `boq`) is required: at least one sprint, one line, every line on a unit, every unit with both sprints (D-R2.6; projects live before R2 without units are not flagged). Needs assessment template (user-facing name since R7; code still says workbook: `modules/scope/workbook/scopeWorkbook.ts`, pure, reusable by the Needs Assessment module): `buildScopeWorkbook` (UBEC styling: title band rows 1–2, headers row 3 (`SCOPE_WORKBOOK_HEADER_ROW`), data from row 4, banded rows by conditional format, locked Amount formula; files "UBEC needs assessment template.xlsx" / "<code> needs assessment.xlsx"; Instructions with the `SCOPE_WORKBOOK_VERSION` stamp, Project, Facility units, BoQ, Sprints, hidden protected Lists; dropdowns, Amount formula, date validation; pre-filled from the project) and `parseScopeWorkbook` (columns by header name, version check, row-level issues, amounts recomputed, a cleared row's stale Amount ignored). `scopeImport.service.ts`: `GET /scope/workbook`, `POST /scope/import/preview` (nothing written) and `/confirm` (same sha256 as the preview or 409 `SCOPE_IMPORT_FILE_CHANGED`; errors 422 `SCOPE_IMPORT_INVALID`; replaces the draft's sprints, units and lines in one transaction; fills only empty project fields from the Project sheet, incl. `siteAddress`, `strategicJustification`, `assumptions`, a primary SCHOOL beneficiary, the delivery model (type applied) and a radial geofence of the workspace default radius from the GPS point; audit `SCOPE_IMPORTED`). The blank template (workspace lists, nothing pre-filled) is `GET /api/v1/scope-workbook` (any web user; Forms & facilities → Facilities); the project needs assessment is also offered in the needs-assessment section (setup step 3). `parseScopeWorkbook` finds the header row in the top 10 rows, so files in the pre-R7 layout (headers in row 1) still import. Live projects refuse import (409 `SCOPE_IMPORT_LIVE_PROJECT`). The programme of works is a `PROGRAMME_OF_WORKS` document (`requiresSignOff`); its sign-off completes `AUTO_SCHEDULE_BASELINE_SET` ("Programme accepted") milestones. ## Environment gotchas (Windows)

- Shell is Git Bash plus PowerShell; there is no Python. Many source files use CRLF line endings, so scripted find-and-replace must normalise `\r\n` or it silently matches nothing; prefer the Edit tool.
- Do not put template literals (backticks) or `${...}` inside inline `node -e "..."` or heredoc commands in bash: they get expanded or break parsing. Write the script or content to a scratch file first.
- The server compiles to CommonJS: ESM-only packages (e.g. `unpdf`) must be loaded with a real dynamic import (see `server/src/integrations/textExtractor.ts`).
