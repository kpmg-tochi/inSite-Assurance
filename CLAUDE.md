# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

InSite Assurance: a multi-tenant field-evidence and drawdown-reconciliation platform for construction finance. An npm-workspaces monorepo, Node 24 (`.nvmrc`), npm 11:

| Workspace | Stack | Role |
| :--- | :--- | :--- |
| `shared` (`@insite/shared`) | TypeScript, Zod, Turf | Enums, every request/DTO schema, permission catalog, default roles, geofence maths, shared data (standards library). Single source of truth for contracts. |
| `server` (`@insite/server`) | Express, Prisma 7 (`pg` adapter), PostgreSQL | REST API under `/api/v1`, voice-note transcription (Whisper; the only model called), S3-compatible storage (local-disk mode in dev/tests), PDF. CommonJS. |
| `web` (`@insite/web`) | React, Vite, React Query, Tailwind 3 | Portal for monitors, lenders, contractors, tenant admins. |
| `mobile` (`@insite/mobile`) | Expo / React Native, SQLite | Offline-first field app with one outbox. |

**This branch (`UBEC`) is being redesigned for one programme client: read `saas_updates/client_flow_redesign.md` first; it overrides earlier decisions where they conflict. Redesign work is tracked in `saas_updates/redesign_r1_implementation_plan.md` (and later R files).** The SaaS migration is run phase by phase from `saas_updates/`. **Before working on a phase, read `saas_updates/saas_implementation_plan.md` sections 2, 3 and 6 (decisions and conventions), then the phase file.** Record findings in the phase file's "Found during implementation" section rather than widening scope. Product background: `Project Context/project_context_current.md`.

## Architecture

**Contracts first.** Every request body and DTO is a Zod schema in `shared/src/schemas`, exported from `shared/src/index.ts`. Web and mobile import types from `@insite/shared`; never hand-write duplicates. New permissions go in `SYSTEM_PERMISSIONS_CATALOG` (`shared/src/enums.ts`) and the default roles (`shared/src/defaultRoles.ts`). New audit actions go in both the shared enum and the Prisma `AuditActionType` enum.

**Server request path.** `server/src/app.ts` mounts routers; most are mounted at `/api/v1/projects`. A project router is wrapped with `guardProjectRoutes` (`server/src/utils/accessControl.ts`), which authenticates any principal (web user, join-code field session, provisioned mobile account), checks tenant/assignment or session binding, and applies lifecycle rules: a DRAFT project serves only the routes in `DRAFT_ROUTE_RE`; an ARCHIVED project is read-only. Route files stay thin (permission guard, `validateBody(schema)`, call a service). Never read a resource by an ID from the body without confirming it belongs to the URL project (`server/src/utils/ownership.ts` loaders). State changes go in one `prisma.$transaction` together with `recordAuditEvent` (hash-chained ledger). Responses are built by explicit serializers, never by spreading Prisma rows. Principals: `req.webUser`, `req.fieldAgent` (`fieldPersonaType`, `origin`, `userId`), `req.mobileUser`.

**Process engine (Phase 7).** Per-project `ProjectProcessConfig` (read via `getProcessConfig`, memoised per request through `server/src/utils/requestContext.ts`; a project with no row behaves as `DEFAULT_PROJECT_PROCESS_CONFIG`). Services branch on it: report approval, hold points, contractor field reporting, identity assurance, the report checks (rules), handover and retention modules. Approval chains are versioned `ApprovalStep` rows: edits write a new version, items in flight keep theirs. Engine: `server/src/modules/process/approvalChain.ts`. Chain types: `REPORT` and `CONTRACT_DEFAULT` (the lender disbursement chain was removed in redesign R1b).

**Cadence and scheduled jobs (Phase 8).** All period maths is pure and shared: `shared/src/utils/reportingPeriod.ts` (`getReportingPeriodForDate`, `listWorkdaysInPeriod`, `nextPeriodStart`; INSPECTION_ONLY has no periods). Server mapping and obligations: `server/src/modules/cadence/cadence.service.ts` (`cadenceSettingsForDate` honours a pending cadence change, `periodKeyForDate`, `fulfilObligation`). Reports and briefs carry `reportingPeriodStart/End` and `dueAt`; one original report per reporter, item and `reportingPeriodStart` (hand-written partial unique index `workday_reports_one_report_per_period`, keep it). Jobs live in `server/src/jobs/` (`brief-dispatch`, `overdue-reports`, `mobilization-reminders`, `attendance-check`, `message-dispatch`, Phase 9 `schedule-variance`, Phase 13 `milestone-deadlines`, Phase 16 `kpi-snapshot`), registered by `registerAllJobs()`; each tick holds `pg_try_advisory_xact_lock` and each unit claims a `JobRun` row via `runUnit(jobName, scopeKey, fn)`. Jobs only touch ACTIVE projects of non-suspended tenants. Tests run a tick with `runJobOnce(name, now)`. `JOBS_ENABLED=false` turns them off in a process. Outbound messages: `server/src/integrations/messaging` (`sendMessage`, adapters console/resend/push, SMS empty; tests read `consoleOutbox` or use `setMessageAdapterOverrides`). Expected participants and attendance: `server/src/modules/mobilization/`; call `syncParticipantForSession` wherever a session is created or its assurance changes. Mobile computes the period from the baseline pack's `cadence` via `mobile/src/utils/projectCadence.ts`; "reported" means a report with `workday_date` inside the period window.

**Schedule (Phase 9).** Pure maths in `shared/src/utils/schedule.ts` (working-day arithmetic, earned-schedule variance in working days with positive = ahead, `projectVariance`, `propagateShift`, `validateScheduleBaseline`, `proposeItemDates`, `formatVariance`, `itemPeriodStatus`). Dates are `YYYY-MM-DD` strings in the project zone on `Project` and `BoqItem` (planned, original, actual); finish-to-start `BoqItemDependency`; `ScheduleRevision` for "Catch Project Up". Server: `server/src/modules/schedule/` (`schedule.service.ts`: view, baseline save, badge refresh, actual dates; `scheduleRevision.service.ts`: preview/create/approve/reject). On a live project with a baseline, dated items move only through a revision; one pending revision per project; a revision that does not move the projected end applies at once, otherwise a different user with `schedule:approve_refactor` approves or rejects, and the proposer may withdraw it while pending; approval re-checks the stored "previous" dates. `actualStartDate` is set via `recordItemActualStart` wherever a report becomes counted; `actualCompletionDate` via `syncActualCompletionDates` inside `refreshCertifiedProgress`. Brief selection (`dispatchTargets` in `morningBrief.service.ts`) uses planned windows (plus overdue items and the `planningTier = PLAN_A` override); `isScheduledToday` no longer exists. The `schedule-variance` job stores the badge (`Project.scheduleStatus` / `scheduleVarianceWorkdays`) shown on the directory, dashboard and executive matrix. Web: `pages/schedule/ProjectSchedulePage.tsx`, `components/schedule/*`, setup step `schedule`.

**Handover, retention and defects (Phase 10).** `Project.constructionPhase` (`ACTIVE_CONSTRUCTION → HANDOVER_IN_PROGRESS → RETENTION_PERIOD → COMPLETED_CLOSED`, only backwards move handover → construction) sits beside `status`; transitions in `server/src/modules/closeout/projectPhase.service.ts`, table and retention maths in `shared/src/utils/retention.ts`. All closeout routes (`closeout.routes.ts`) answer 404 unless `enableHandoverModule` / `enableRetentionModule` is on (`closeoutGate.ts`). After construction: `assertConstructionOngoing` refuses briefs; `LIVE_PROJECT_WHERE` excludes the project from construction jobs; field sessions may only write defect work (`FIELD_DEFECT_WORK_RE` in `accessControl.ts`). Public handover API: separate router at `/api/v1/public/handover` mounted before the JSON parser (`handoverPublic.routes.ts`/`.service.ts`): token hash lookup with one generic 404, OTP with lockout, session JWT on a derived key (never accepted by `verifyClaims`), uploads quarantined under `.../handover/{linkId}/` (capture registration refuses them; media endpoint serves them to `handover:review_feedback` only, documents as attachments). Stakeholder text is sanitised plain text (`shared/src/utils/handoverText.ts`), rendered by `RichTextView`, never as HTML. Retention is held against recorded payments (see Payments below); `Project.retentionHeldNgn` is the balance still held, `retentionReleasedNgn` the total released. Release: record a `RETENTION_RELEASE` payment; `GET /retention` reports the balance and the liability period. Defect sides are by organisation (`defectViewerFor`), not role. Job `defect-reminders`. Mobile: `DefectsScreen`, outbox kind `DEFECT_ACTION` (payload carries the action, waits on its captures). `WEB_APP_BASE_URL` builds link URLs. Defect notifications are aimed: contractor-facing ones use `createWebNotification({ targetOrganizationId })` plus mobile `DEFECT_UPDATE` to sessions bound to that contractor by join code; monitoring-side ones set `hideFromProjectContractors` (both honoured by `buildWebNotificationFilter`). Repair evidence follows `allowContractorFieldReporting`: off means the verifier captures and closes (`evidenceCapturedBy: MONITOR`). Handover files above 5 MB use multipart (`/uploads/multipart/start|parts|status|complete`, a signed upload ticket, `storageService.startMultipartUpload` and friends; local storage emulates parts under `<object>.parts/`).

**Delivery models (Phase 11).** Client rules are data on a project type or the tenant (decision J). `Organization.parentOrganizationId` forms a hierarchy (max 5 levels, cycles refused by `validateOrganizationParent` in `shared/src/utils/organizationHierarchy.ts`; server helpers in `server/src/modules/organizations/hierarchy.ts`). `Project.owningOrganizationId` is the accountable owner; the funder is still `lenderOrganizationId` (shown through terminology). Visibility: `projectAccessBranch` in `accessControl.ts` is the one rule for lists and the guard (assigned, or `projects:view_all_tenant`, or `projects:view_organization_tree` + owner in the user's subtree, expressed as nested parent relations so it composes into any `where`); mobile accounts follow the same rule. Approval steps carry `organizationScope` (`ANY`, `PROJECT_OWNER`, `PROJECT_OWNER_OR_ANCESTOR`, `FUNDER`); every `gateForStep` call must pass `orgContext` from `orgContextForStep` (no bypass, not even the platform super admin). `ProjectType` (`server/src/modules/projectTypes/`) references a workflow template and holds `ProjectTypeConfigSchema` (every key defaulted; reserved keys for Phases 12–16). Applying a type to a draft (`applyProjectTypeToProject`, from the Basics step or draft creation) copies the template, writes `projectTypeSnapshotJson` + `projectTypeVersion`, pre-fills owner/funder/reporting without overwriting saved values, and audits `PROJECT_TYPE_APPLIED`; on a live project the type is locked (409 `PROJECT_TYPE_LOCKED`). Read a project's rules with `resolveProjectTypeConfig(snapshot)` (null = no type = pre-Phase-11 behaviour); never read the live type for a project's rules. A tenant with active types must give new drafts a type. Regions (`server/src/modules/regions/`) are two levels. Beneficiaries are saved with the Parties step (exactly one primary). Terminology: `Tenant.terminologyLabels`, keys fixed in `shared/src/terminology.ts`; web uses `useTerm()` from `auth-context`, server uses `terminologyForProject` / `resolveTerminology`, mobile reads `useActiveBranding().terminology`. Terms are display only: API fields, enum values, audit text and AI prompts keep canonical names. Directory, executive matrix and the portfolio dashboard (`GET /projects/portfolio/overview`, permission `projects:view_portfolio`, web `/app/portfolio`, the landing page for holders) accept `projectTypeId`, `regionId` (includes its areas) and `owningOrganizationId` filters. `projectId = all` is a GET-only listing sentinel, except the two web-notification read endpoints (`ALL_PROJECTS_WRITE_RE`).

**Credentials and milestone payments (Phase 12).** Professional registration is policy, not a hard rule: `resolveCredentialPolicy(tenant.credentialPolicyJson, project.projectTypeSnapshotJson)` (`shared/src/schemas/credentials.schema.ts`) gives `certifier` and `fieldAssurance` as `REQUIRED | OPTIONAL | HIDDEN` (project type → tenant → platform default `REQUIRED`). Server decisions go only through `server/src/modules/credentials/credentialPolicy.service.ts`: `certifierCannotActReason` (viewer `canAct` gates), `fieldAssuranceRegistration` (join and assurance submission). Forms use `credentialFieldRules(requirement, subject)` (web `components/credentials/CertifierRegistration.tsx`, mobile `utils/assuranceRegistration.ts`); never test for a licence directly. Registration bodies are a tenant table (`ProfessionalRegistrationBody`, routes under `/api/v1/credentials`, provisioned with every tenant); users store `professionalRegistrationBodyCode/Number`; `ValuationReport.certifierLicenseType/Number` (nullable, body code) plus `certifierRegistrationBodyName/Prefix` snapshot the registration so PDFs print as signed (`formatRegistration`; nothing printed without a number). Permissions and segregation never depend on the policy.

**Streams and inspections (Phase 14).** `ReportingCadence` has `QUARTERLY` (calendar quarters from `cadenceQuarterAnchorMonth`, default January; the same field name on `Project`, `CadenceSettings`, the cadence DTO and the Reporting step). `ProjectReportingStream` rows (`server/src/modules/cadence/streams.service.ts`): a project with none runs the Phase 8 implicit stream unchanged; with any active stream, only streams are owed. `ITEM_REPORTS` streams owe per-item obligations (tagged `streamId`) for the personas of their roles (optionally one package); `INSPECTION` streams owe one obligation per period (`boqItemId` null, scope `inspection`, late after due + grace + `submissionDeadlineDays`). Period maths for a stream goes through `streamCadenceRow(project, stream)` + the usual `cadenceSettingsForDate` (its own pending change applies per stream). Item reports take the period of the reporter's stream (`itemStreamForReporter`); briefs only for item streams (`generateDispatchForProject(..., stream)`; `brief-dispatch` and `overdue-reports` iterate streams). Applying a type with `reportingStreams` (role codes) replaces a draft's streams. Checklist templates are tenant-level and versioned by code (`modules/inspections/checklistTemplates.service.ts`: a used version is never edited). `validateInspectionAnswers` (`shared/src/utils/inspectionChecklist.ts`) is the one rule set; missing photos are never a server error (the omission check's inspection mode flags them, engine `RULES`; the phone requires them). `SiteInspectionReport` (`inspections.service.ts`): idempotent on `clientReportId`, captures linked per item (`siteInspectionReportId` + `checklistItemKey`; other projects refused), report approval chain with subject `SITE_INSPECTION`, failed items auto-raise `InspectionFinding`s aimed at the only/main contractor (`findings.service.ts`, sides via `defectViewerFor`). Supervision workload (`supervision.service.ts`): users in a type's `supervision.supervisorRoleCodes`, warn-only. Mobile: pack `inspections` (streams owed, templates by visit type), `InspectionScreen` (draft in SQLite `inspection_drafts`), outbox kinds `SITE_INSPECTION` and `FINDING_RESOLUTION` behind their captures, `InspectionFindingsScreen`. Web: `/app/projects/:id/inspections`, `InspectionOverviewCard`, Reporting-step `ReportingStreamsEditor`, Settings → "Inspections & supervisors", team-step `TeamWorkloadNotice`.

**Contract milestones and documents (Phase 13).** Contracts in `shared/src/schemas/contract.schema.ts`; due-date maths in `shared/src/utils/contractMilestones.ts` (`computeMilestoneDueDates`, `deriveMilestoneStatus`). Document register: `server/src/modules/documents/` (tenant `DocumentType`s provisioned from `DEFAULT_DOCUMENT_TYPES`; `ProjectDocument` + versions + sign-offs). Files go up through `/evidence/presign` with `PROJECT_DOCUMENT` (keys under `.../project_document/`); the server reads size, type and SHA-256 from storage. The contractor side (by organisation) sees only types with `visibleToContractors` that are project-wide or its own, plus its own uploads; the media endpoint applies the same rule to document keys (`assertDocumentObjectReadable`). CP evidence is `ConditionPrecedent.evidenceDocumentId`. Milestones (`server/src/modules/contracts/milestones.service.ts`): rows come from the type snapshot's `contractMilestones` (`syncContractMilestones`, called on type apply, contractor changes and activation), dates from the project anchors `contractAwardDate`/`contractSignedDate`/`kickoffDate`/activation (setup step `contract`) or another milestone's completion, or `anchorDateOverride` (replacements, extensions). Every anchor change goes through `recomputeMilestoneDates`/`recomputeAndAudit`. Reads derive PENDING/DUE/OVERDUE for today; the job `milestone-deadlines` stores status, notifies once per state, and opens a default case for an overdue `AUTO_CONTRACTOR_ON_SITE` milestone. Automatic completions go only through `autoCompleteMilestones`: the telemetry in-geofence check-in hook (`recordContractorOnSite`), the kick-off notice and held record (`kickoff.service.ts`), and the schedule baseline (`applyScheduleBaseline`, also used by programme-of-works acceptance). Default cases (`defaultCases.service.ts`) run on the third chain type `CONTRACT_DEFAULT` (subject `CONTRACT_DEFAULT_CASE`; the last step is the system step `contracts:decide_default`; the default is created lazily per project). Termination is `ProjectContractor.contractStatus = TERMINATED`, never project ARCHIVED. It deactivates codes, revokes sessions and waives open milestones. Terminated contractors are skipped by join codes, briefs and model rules. Replacement (`/contractors/:id/replace`) moves items below 100% certified. Milestone templates and kick-off rules are edited in the project-type editor (`components/deliveryModels/ContractRulesEditor.tsx`). Web: `/app/projects/:id/documents`, `/milestones`, `/kickoff`, the setup step `ContractStep`, `components/contracts/*`, `components/documents/*` (`DocumentPicker`).

**Completion and closure (Phase 15).** Rules are the project type's `closure` config (`shared/src/schemas/closure.schema.ts`; read with `closureConfigOf(snapshot)`, gates only for typed projects via `cocGateOn`). Certificate of Completion (`server/src/modules/completion/completion.service.ts`): draft (`completion:draft_certificate`, needs an approved/accepted `FINAL_EVALUATION` inspection when `requireFinalEvaluationBeforeCoc`) → signatures in the slots copied onto the certificate (`slotsJson`: permission, optional role code, organisation scope incl. `MONITOR`, one slot per person) → the beneficiary slot is recorded by staff from an uploaded signed paper copy plus attestation (D-15.1 default; `HANDOVER_LINK` signing is not built, `HandoverLink.purpose` has only `HANDOVER`) → the last signature issues it in the same transaction: PDF (`integrations/closure-pdf.service.ts`) stored with `storeGeneratedDocument` (signed off by the staff signatories), `practicalCompletionDate` if empty, the handover ceremony milestone (anchor `COC_ISSUED`; created as `handover-ceremony` when the type has none), `AUTO_COC_ISSUED` milestones done, aimed notifications. Revoke (`completion:revoke_certificate`, reason) only before a handover is accepted: archives the PDF, reopens `AUTO_COC_ISSUED` milestones, dates move. Gates (`closure.requireCocFor`): `HANDOVER_TO_RETENTION` and `PROJECT_CLOSE` in `checkTransition`; `FINAL_PAYMENT` is not a block (payments are made outside the platform): a FINAL payment or retention release recorded without an issued CoC is flagged as an exception on the payment. Reviewing an accepted handover issues the handover certificate (`handoverCertificate.service.ts`) and completes `AUTO_HANDOVER_ACCEPTED` milestones. Closure checklist (`closure.service.ts`): `ClosureChecklistItemState` rows created on entering handover (`ensureClosureChecklist`, lazily on read), automatic kinds evaluated live, manual by `closure:manage_checklist` (or the item permission), `AUDIT_SIGNOFF` by `closure:audit_signoff` and never waivable; `beforeClose` gates `COMPLETED_CLOSED`, `beforeArchive` gates `archiveProject` (once the checklist exists); closing/archiving freezes met items. Anchor `PROJECT_CLOSED` (close date) dates the post-closure evaluation; an accepted final evaluation completes dated `AUTO_FINAL_EVALUATION_APPROVED` milestones. Ratings (`ratings.service.ts`, tenant `ratingCriteriaJson`, `/api/v1/closure/rating-criteria`): one per contractor, stage and rater; hidden from the contractor side unless `shareRatingsWithContractor`; `/api/v1/closure/organizations/:id/ratings`. Lessons (`lessons.service.ts`): drafts for the project team, published to `/api/v1/closure/lessons` (`lessons:view`), shared ones reach the contractor with an aimed notification. Closure pack (`closurePack.service.ts`): `POST /projects/:id/closure-pack` (also on ARCHIVED projects, `ARCHIVED_WRITE_RE`) queues an in-process export (tests: `setClosurePackScheduler` + `runClosurePackExport`; job `closure-packs` sweeps), ZIP via `utils/zipWriter.ts` (index PDF, manifest with SHA-256, documents, certificates, valuation PDFs, inspection summaries, audit CSV + chain verification) stored as `CLOSURE_FILE`. The `milestone-deadlines` job covers active projects in every phase. Web: Completion section (`components/closure/CompletionSection.tsx`) on the Closure tab (open to `completion:*` holders, since the default signatories have no handover permission) and on the Handover tab, `/app/projects/:id/closure`, rating criteria card in Settings → Tenant Settings, `/app/lessons`, `/app/organizations/:id/ratings`, type editor `ClosureRulesEditor`.

**Programme KPIs (Phase 16).** Catalogue in `shared/src/schemas/kpi.schema.ts` (21 KPIs: key, stage, unit, direction, `periodBased`, `defaultTarget`; `kpiValue`, `kpiStatus`, `resolveKpiTargets`); tenants only set `ProjectTypeConfig.kpiTargets` (`{ [key]: { target, shown } }`, editor `components/deliveryModels/KpiTargetsEditor.tsx`). Targets are read from the **live** project type (reporting settings, applied at once), unlike every other type rule. Engine: `server/src/modules/kpis/kpiEngine.ts`, one pure function per KPI over per-project facts returning `{numerator, denominator}` or null (= not tracked, never shown as 0); facts are loaded in batches by `kpiFacts.ts` (add a source there, never a per-project query). A portfolio value is the sum of numerators over the sum of denominators. `GET /api/v1/kpis` (`kpis:view`, the directory's visibility with ACTIVE and ARCHIVED projects, Phase 11 filters, `from`/`to`) and `GET /projects/:id/kpis`. Job `kpi-snapshot` (one `JobRun` per tenant-day) writes `KpiSnapshot` rows for the current month and backfills earlier months once; trends read them. Periods are the tenant's (`Tenant.timezone` via `tenantKpiZone`/`safeZone`): the default period, the job day and month, trend months, and the dating of events counted into a period (approvals, releases, CoC issue); project deadlines and on-time checks stay in the project zone (`loadKpiFacts(projects, period, periodZone, now)`). Web: `/app/kpis` (`pages/kpis/ProgrammeKpisPage.tsx`), `components/kpis/*` (status chips always icon + label; chart colours from `--kpi-*` CSS variables), `ProjectKpisCard` on the project dashboard. The project type editor (`components/deliveryModels/ProjectTypesTab.tsx`) has a control for every `ProjectTypeConfig` key (`DocumentRulesEditor`, `MonitoringRulesEditor`, `CadenceFields`, plus the Phase 13/15/16 editors); a new config key needs an editor section too. `GET /rbac/roles` and `GET /inspection-templates` also accept `project_types:manage` for its pickers. Delivery docs: `saas_updates/configuration_reference.md` (every setting from Phases 11–16) and `saas_updates/demo_script_programme_delivery.md`; keep them in step when settings change.

**Evidence, progress and payments (redesign R1b).** The lender product (IPC claims, reconciliation, evidence ratings, valuations, tranches, conditions precedent, direct milestone release, disbursement chain) is deleted. Mobile captures register as `FieldEvidenceLog` and link to a human-confirmed `WorkdayReport`; `server/src/modules/evidence/evidenceProvider.ts` defines the counted report statuses and supersession. Progress: `modules/progress/progress.service.ts` (`recordCountedReport` wherever a report becomes counted; `refreshProjectProgress` sets `BoqItem.cumulativeCertifiedPct` (legacy name) from counted reports and the budget-weighted `Project.certifiedProgressPct`). Payments are made outside the platform and recorded in `modules/payments` (`ProjectPayment`: INTERIM, FINAL, RETENTION_RELEASE; source MANUAL, ERP later; permissions `payments:view`, `payments:record`): recording holds retention at the project percentage (a different amount needs a reason), keeps `disbursedToDateNgn` (net paid) and the retention totals in step in the same transaction, stores exception codes (`FINAL_BEFORE_COC`, `RETENTION_RELEASE_*`, `PAID_ABOVE_CONTRACT_SUM`) and notifies `PAYMENT_EXCEPTION`; a wrong entry is voided with a reason, never deleted. Amounts are computed server-side.

**No AI (client requirement, redesign decision Z).** The platform calls no language or vision model; the only model is Whisper for voice-note transcription (`server/src/integrations/whisper.service.ts`). Checks, briefs and suggestions are deterministic rules (`workday-reports/reportRules.ts`, `standards/standardsRules.ts`, `morning-briefs/briefPersona.ts`). Never add an AI provider or AI wording. Post-response checks (omission + standards) run off the request path (`server/src/modules/workday-reports/aiOmissionCheck.ts`; internal "ai" names there are legacy and go with R2–R5). Test hook: `setAiOmissionCheckScheduler`.

**Web.** `web/src/api/<area>` fetchers, `web/src/queries/<area>` and `web/src/mutations/<area>` React Query hooks; mutation hooks own sonner toasts (pages do not toast again). Gate UI with `hasPermission` from `web/src/lib/auth-context.tsx`; never infer roles from permission combinations or role codes. Reuse `components/common` and `components/table/StandardTable`. Project setup is a step registry (`PROJECT_SETUP_STEPS` in shared, `web/src/pages/projects/setup/stepRegistry.ts`); the same step pages serve `/setup/:step` (draft) and `/settings/:step` (live). New `navigate()` calls must use `useGuardedNavigate` to get the unsaved-changes guard. Demo defaults belong behind the demo flag only.

**Mobile.** All persistence goes through `mobile/src/storage/*` (SQLite migrations in `storage/db/migrations.ts`); one outbox (`storage/outbox`), no ad-hoc queues; client IDs are UUIDs; never send display strings, `file://` paths or base64 as record fields; never show a verification state the app did not compute. Persona-dependent wording lives in `mobile/src/utils/personaCopy.ts`.

## Environment gotchas (Windows)

- Shell is Git Bash plus PowerShell; there is no Python. Many source files use CRLF line endings, so scripted find-and-replace must normalise `\r\n` or it silently matches nothing; prefer the Edit tool.
- Do not put template literals (backticks) or `${...}` inside inline `node -e "..."` or heredoc commands in bash: they get expanded or break parsing. Write the script or content to a scratch file first.
- The server compiles to CommonJS: ESM-only packages (e.g. `unpdf`) must be loaded with a real dynamic import (see `server/src/integrations/textExtractor.ts`).
